# Движок классификации данных для системы "Медикаменте"

## 1. Введение

### 1.1 Цель решения

Спроектировать движок для автоматической классификации данных перед их пакетной загрузкой в аналитическое хранилище с учётом принципов Privacy by Design.

### 1.2 Ключевые требования

1. Автоматическая классификация: определение уровня конфиденциальности данных
2. Адаптация к изменениям схемы: обработка структурных изменений входных данных
3. Многослойное хранилище: организация данных с учётом конфиденциальности
4. Масштабируемость: поддержка роста объёмов данных
5. Измеримость: метрики эффективности классификации

## 3. Компоненты движка

### 3.1 Ingestion Layer (Слой загрузки)

| Компонент          | Технология            | Функция                                              |
|--------------------|-----------------------|------------------------------------------------------|
| File Connector     | Python/Pandas         | Загрузка Excel, CSV, JSON файлов с файлового сервера |
| Database Connector | SQLAlchemy            | Подключение к 1С (PostgreSQL/MSSQL)                  |
| API Connector      | Python/Requests       | REST/SOAP интеграции (лаборатория)                   |
| Schema Registry    | Apache Avro/Confluent | Хранение и версионирование схем данных               |

### 3.2 Classification Layer (Слой классификации)

#### 3.2.1 Schema Analyzer

Анализирует структуру данных и обнаруживает изменения схемы.

| Функция             | Описание                                |
|---------------------|-----------------------------------------|
| Schema inference    | Автоматическое определение типов данных |
| Change detection    | Обнаружение новых/удалённых полей       |
| Compatibility check | Проверка совместимости версий           |
| Lineage tracking    | Отслеживание происхождения данных       |

#### 3.2.2 PII/PHI Detector

Обнаружение персональных и медицинских данных:

| Метод                          | Применение                       | Примеры                                                   |
|--------------------------------|----------------------------------|-----------------------------------------------------------|
| Regex Patterns                 | Структурированные идентификаторы | Паспорт: `\d{2}\s?\d{2}\s?\d{6}`, ИНН: `\d{10,12}`, СНИЛС |
| Named Entity Recognition (NER) | Имена, адреса, организации       | ФИО, названия улиц                                        |
| Medical Dictionary             | Медицинские термины              | МКБ-10 коды, названия препаратов                          |
| Pattern Matching               | Форматы данных                   | Email, телефон, даты                                      |

#### 3.2.3 Classification Rules Engine

Правила классификации на основе обнаруженных данных:

| Уровень         | Категория       | Правила                                                | Примеры данных    |
|-----------------|-----------------|--------------------------------------------------------|-------------------|
| 4 (Критический) | PHI, Passport   | `contains_diagnosis OR contains_passport`              | Диагнозы, паспорт |
| 3 (Высокий)     | PII Bundle, FIN | `(contains_name AND contains_dob) OR contains_payment` | ФИО+ДР, платежи   |
| 2 (Средний)     | PII Basic       | `contains_phone OR contains_email OR contains_address` | Контакты          |
| 1 (Базовый)     | Internal        | `NOT contains_pii AND NOT contains_phi`                | Служебные ID      |

#### 3.2.4 ML Classifier

Для неструктурированных данных (текст, документы).

Присвоение тегов классифицированным данным:

| Тег         | Описание            | Уровень | Требования            |
|-------------|---------------------|---------|-----------------------|
| TAG-PHI-001 | Диагноз пациента    | 4       | HSM + AES-256 + audit |
| TAG-PHI-002 | Результаты анализов | 4       | HSM + AES-256 + audit |
| TAG-PII-001 | ФИО пациента        | 3       | AES-256 + RBAC        |
| TAG-PII-002 | Паспортные данные   | 4       | HSM + AES-256         |
| TAG-PII-003 | Контактные данные   | 2       | AES-256               |
| TAG-FIN-001 | Данные платежа      | 3       | AES-256 + PCI DSS     |
| TAG-INT-001 | Внутренний ID       | 1       | Standard              |

### 3.3 Transformation Layer (Слой трансформации)

#### 3.3.1 Anonymization Engine

| Метод                | Применение              | Параметры     |
|----------------------|-------------------------|---------------|
| K-anonymity          | Квази-идентификаторы    | k ≥ 5         |
| L-diversity          | Чувствительные атрибуты | l ≥ 3         |
| T-closeness          | Распределение атрибутов | t ≤ 0.2       |
| Differential Privacy | ML-модели               | ε ≤ 1.0       |
| Pseudonymization     | Идентификаторы          | Token mapping |
| Suppression          | Редкие значения         | Threshold < 5 |

## 4. Аналитическое хранилище данных (Medallion Architecture)

### 4.1 Описание слоёв

| Слой          | Данные                                      | Защита                                   | Доступ                      | Retention     |
|---------------|---------------------------------------------|------------------------------------------|-----------------------------|---------------|
| Bronze        | Сырые данные с тегами классификации         | Encrypted at-rest, pseudonymized IDs     | ETL pipelines only          | 90 дней       |
| Silver        | Очищенные, валидированные, токенизированные | All PII tokenized, referential integrity | Data Engineers (с approval) | 1 год         |
| Gold          | Полностью анонимизированные, агрегированные | K-anonymity, no direct identifiers       | Analysts, BI tools          | Бессрочно     |
| Privacy Vault | Маппинг Token <-> Real ID                   | HSM-protected, strict audit              | DPO only (legal basis)      | По требованию |

### 4.2 Дополнительные меры защиты

| Мера                    | Применение                      | Реализация                      |
|-------------------------|---------------------------------|---------------------------------|
| Row-Level Security      | Ограничение доступа к строкам   | PostgreSQL RLS policies         |
| Column-Level Encryption | Шифрование отдельных колонок    | TDE + field encryption          |
| Dynamic Data Masking    | Маскирование при отображении    | SQL Server DDM / custom views   |
| Audit Logging           | Логирование всех запросов       | ELK + custom audit tables       |
| Data Retention          | Автоматическое удаление         | Scheduled jobs, GDPR compliance |
| Access Review           | Периодический пересмотр доступа | Quarterly review process        |

## 5. Метрики эффективности классификации

### 5.1 Основные метрики

| Метрика             | Формула               | Целевое значение | Критический порог |
|---------------------|-----------------------|------------------|-------------------|
| Accuracy**          | (TP + TN) / Total     | > 95%            | < 90%             |
| Recall (PII/PHI)    | TP / (TP + FN)        | > 99%            | < 95%             |
| Precision**         | TP / (TP + FP)        | > 90%            | < 80%             |
| F1-Score**          | 2 * (P * R) / (P + R) | > 0.94           | < 0.87            |
| False Negative Rate | FN / (FN + TP)        | < 1%             | > 5%              |

### 5.2 Операционные метрики

| Метрика                | Описание                      | Целевое значение   |
|------------------------|-------------------------------|--------------------|
| Processing Time        | Время классификации записи    | < 100 ms/record    |
| Throughput             | Записей в секунду             | > 1000 records/sec |
| Schema Drift Detection | Обнаружение новых полей       | 100%               |
| Classification Latency | E2E время от загрузки до тега | < 5 минут          |
| Error Rate             | Ошибки обработки              | < 0.1%             |

### 5.3 Как метрики помогают оптимизации

1. Recall < target -> Добавить новые regex patterns, расширить NER модель
2. Precision < target -> Уточнить правила, добавить исключения
3. Processing time > target -> Оптимизировать пайплайн, добавить кэширование
4. Schema drift detected -> Автоматически классифицировать новые поля

## 7. Заключение

### 7.1 Ключевые особенности решения

1. Автоматическая классификация: ML + Rules Engine для обнаружения PII/PHI
2. Адаптация к изменениям: Schema Registry отслеживает изменения структуры
3. Многослойная защита: Medallion Architecture (Bronze → Silver → Gold)
4. Privacy Vault: изолированное хранение маппинга Token ↔ ID
5. Измеримость: метрики Accuracy, Recall, Precision, F1
6. Масштабируемость: Kubernetes, Kafka, Spark для роста нагрузки

### 7.2 Соответствие Privacy by Design

| Принцип PbD             | Реализация в решении                     |
|-------------------------|------------------------------------------|
| Проактивность           | Автоматическая классификация до загрузки |
| Privacy by Default      | Все данные классифицируются и защищаются |
| Встроенная защита       | Шифрование и анонимизация в пайплайне    |
| Полная функциональность | Аналитика на Gold Layer без компромиссов |
| End-to-End Security     | Защита от источника до хранилища         |
| Прозрачность            | Audit logging, метрики, lineage          |
| User-Centric            | Privacy Vault для права на удаление      |
