# Cutover-план миграции системы «Медикаменте»

## 1. Анализ текущей ситуации

### 1.1 Описание существующей системы (AS-IS)

| Компонент                 | Технология                           | Характеристики                         |
|---------------------------|--------------------------------------|----------------------------------------|
| Хранение данных пациентов | Excel-файлы на файловом сервере      | Patients.xlsx, Journal-Doctor-FIO.xlsx |
| Хранение медданных        | Файлы на общем диске                 | Data files (сканы, результаты, снимки) |
| Бухгалтерия               | 1С Бухгалтерия (файловый режим)      | Платежи, финансовые данные             |
| Склад                     | 1С Торговля и склад (файловый режим) | Учёт ТМЦ, медикаментов                 |
| Касса                     | ККМ (TCP/IP-OLE)                     | Приём платежей                         |
| Почта                     | Exchange Mail Server                 | Внутренняя почта, обмен с лабораторией |
| Интеграции                | OLE, SMB/CIFS, Email                 | Синхронные, незащищённые               |

### 1.2 Требования к новой архитектуре (TO-BE)

1. Privacy by Design: соответствие всем 7 принципам
2. Шифрование: AES-256 at-rest, TLS 1.3 in-transit
3. IAM: Keycloak с OAuth2/OIDC, MFA, RBAC
4. Аудит: полное логирование доступа к ПДн
5. Соответствие ФЗ-152: защита персональных данных
6. API-first: REST API для всех интеграций
7. Масштабируемость: контейнеризация, микросервисы

### 1.3 Бизнес-цели миграции

| Цель                  | Приоритет   | Метрика успеха               |
|-----------------------|-------------|------------------------------|
| Соответствие ФЗ-152   | Критический | 100% шифрование ПДн          |
| Минимизация downtime  | Высокий     | < 4 часов суммарно           |
| Сохранность данных    | Критический | 0% потерь                    |
| Непрерывность бизнеса | Высокий     | Приём пациентов без перебоев |
| Обучение персонала    | Средний     | 100% сотрудников обучены     |

## 2. Выбор стратегии миграции

### 2.1 Анализ вариантов

| Стратегия             | Описание                                   | Преимущества                                            | Недостатки                                              |
|-----------------------|--------------------------------------------|---------------------------------------------------------|---------------------------------------------------------|
| High-level Design     | Полное перепроектирование с учётом домена  | Чистая архитектура, оптимальный дизайн                  | Длительные сроки, высокий риск, "big bang"              |
| Parallel Run          | Параллельный запуск старой и новой системы | Низкий риск, возможность сравнения, постепенный переход | Двойные затраты на инфраструктуру, синхронизация данных |
| Branch by Abstraction | Постепенный перенос слой за слоем          | Минимальный риск, непрерывная работа                    | Сложность абстракций, длительные сроки                  |

### 2.2 Обоснование выбора: PARALLEL RUN

Выбранная стратегия: Parallel Run (Параллельный запуск)

#### Причины выбора:

1. Критичность данных
   - Медицинские данные требуют максимальной защиты
   - Возможность сравнения результатов в двух системах
   - Верификация корректности миграции данных

2. Требования бизнеса
   - Клиника не может остановить приём пациентов
   - Необходима непрерывность финансовых операций
   - Возможность быстрого отката при проблемах

3. Регуляторные требования
   - ФЗ-152 требует сохранности данных
   - Возможность аудита процесса миграции
   - Документирование соответствия на каждом этапе

4. Управление рисками
   - Постепенный перевод пользователей
   - Тестирование на реальных данных
   - Минимизация влияния на пациентов

#### Ограничения выбранной стратегии:

| Ограничение                               | Митигация                                       |
|-------------------------------------------|-------------------------------------------------|
| Двойные затраты на инфраструктуру         | Использование облачной инфраструктуры для TO-BE |
| Синхронизация данных между системами      | CDC (Change Data Capture) + очереди сообщений   |
| Обучение персонала работе в двух системах | Поэтапное обучение по ролям                     |
| Сложность поддержки двух систем           | Чёткое разделение ответственности               |

## 4. План отката (Rollback Plan)

### 4.1 Триггеры для отката

| Критерий               | Порог           | Решение                 |
|------------------------|-----------------|-------------------------|
| Потеря данных          | > 0 записей     | Немедленный откат       |
| Критические баги       | > 0 блокирующих | Откат в течение 2 часов |
| Время простоя          | > 4 часов       | Откат                   |
| Ошибки платежей        | > 1% транзакций | Откат модуля платежей   |
| Недоступность сервисов | > 30 минут      | Откат                   |

## 7. Критерии успеха миграции

### 7.1 KPI миграции

| Метрика                         | Целевое значение  | Критический порог |
|---------------------------------|-------------------|-------------------|
| Потеря данных                   | 0%                | 0% (no-go)        |
| Общий downtime                  | < 4 часов         | 8 часов           |
| Время cutover weekend           | < 48 часов        | 72 часа           |
| Ошибки после миграции           | < 5 critical bugs | 10 critical bugs  |
| Удовлетворённость пользователей | > 80%             | 60%               |
| Соответствие ФЗ-152             | 100%              | 100% (no-go)      |
| Производительность              | ≥ AS-IS           | -20% от AS-IS     |

### 7.2 Чеклист Go/No-Go

#### Этап 1 -> Этап 2 (Parallel Run)
- Все сервисы TO-BE развёрнуты и работают
- Первичная миграция данных завершена
- CDC-синхронизация работает
- Smoke-тесты пройдены
- Мониторинг настроен

#### Этап 2 -> Этап 3 (Cutover)
- Parallel run завершён успешно (4 недели)
- Расхождений данных нет
- UAT пройден
- Security-тест пройден
- Все пользователи обучены
- Rollback plan протестирован
- DPO подтвердил соответствие ФЗ-152

## 8. Заключение

Разработанный cutover-план основан на стратегии Parallel Run, которая обеспечивает:

1. Минимальный риск: параллельная работа систем позволяет верифицировать данные
2. Непрерывность бизнеса: клиника работает без остановки
3. Возможность отката: план отката с временем < 2 часов
4. Соответствие требованиям: ФЗ-152 на каждом этапе

Общая длительность: 15 недель
Критический путь: Миграция данных -> Parallel Run -> Cutover Weekend
Ключевой фактор успеха: Качество синхронизации данных между AS-IS и TO-BE
