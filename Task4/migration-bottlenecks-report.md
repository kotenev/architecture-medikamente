# Оценка узких мест при миграции системы «Медикаменте»

## 1. Введение

### 1.1 Контекст миграции

Компания "Медикаменте" планирует миграцию с текущей устаревшей архитектуры (AS-IS) на современную архитектуру с реализацией принципов Privacy by Design (TO-BE). Текущая система характеризуется:

- Хранение данных: Excel-файлы на файловом сервере
- **Бизнес-системы: 1С Бухгалтерия и 1С Торговля в файловом режиме
- Интеграции: OLE, TCP/IP-OLE, Email
- Безопасность: Отсутствует шифрование, RBAC, аудит

### 1.2 Цели миграции

1. Переход на современную микросервисную/модульную архитектуру
2. Реализация Privacy by Design и соответствие ФЗ-152
3. Внедрение шифрования данных at-rest и in-transit
4. Централизованное управление идентификацией (IAM)
5. Автоматизация процессов и мониторинг

## 2. Ключевые процессы и компоненты миграции

### 2.1 Затрагиваемые компоненты

| Компонент AS-IS           | Компонент TO-BE                  | Тип изменения   |
|---------------------------|----------------------------------|-----------------|
| Файловый сервер (Excel)   | PostgreSQL + Document Store      | Полная замена   |
| 1С Бухгалтерия (файловый) | 1С Бухгалтерия (серверный) + API | Модернизация    |
| 1С Торговля (файловый)    | 1С Торговля (серверный) + API    | Модернизация    |
| ККМ (TCP/IP-OLE)          | ККМ + REST API                   | Интеграция      |
| Exchange Mail Server      | Exchange + S/MIME + API Gateway  | Усиление        |
| SMB/CIFS без шифрования   | SMB 3.0 + TLS 1.3                | Модернизация    |
| Нет IAM                   | Keycloak (OAuth2/OIDC)           | Новый компонент |
| Нет KMS                   | HashiCorp Vault + HSM            | Новый компонент |
| Нет мониторинга           | Wazuh + ELK Stack                | Новый компонент |

### 2.2 Критические бизнес-процессы

1. Регистрация пациентов: миграция данных из Patients.xlsx
2. Ведение журналов врачей: миграция Journal-Doctor-FIO.xlsx
3. Приём платежей: интеграция ККМ → 1С
4. Обмен с лабораторией: защита канала передачи результатов
5. Складской учёт: синхронизация 1С систем

## 5. Риски снижения производительности

### 5.1 Идентифицированные риски

| ID   | Риск                                | Категория          | Вероятность | Влияние | Митигация                                     |
|------|-------------------------------------|--------------------|-------------|---------|-----------------------------------------------|
| Р-01 | Замедление при шифровании данных    | Производительность | Средняя     | Среднее | Аппаратное ускорение (AES-NI), HSM            |
| Р-02 | Задержки из-за API Gateway          | Latency            | Средняя     | Среднее | Кэширование, оптимизация маршрутизации        |
| Р-03 | Блокировки при миграции данных      | Доступность        | Высокая     | Высокое | Инкрементальная миграция, blue-green          |
| Р-04 | Перегрузка ETL-пайплайна            | Производительность | Средняя     | Среднее | Параллельная обработка, batch processing      |
| Р-05 | Недостаточная производительность БД | Производительность | Средняя     | Высокое | Правильное индексирование, connection pooling |
| Р-06 | Overhead мониторинга (SIEM)         | Ресурсы            | Низкая      | Низкое  | Sampling, фильтрация логов                    |
| Р-07 | Деградация при MQ-интеграции        | Latency            | Низкая      | Среднее | Правильный sizing очередей                    |

### 5.2 Архитектурные рекомендации по производительности

1. Шифрование:
   - Использовать AES-NI для аппаратного ускорения
   - Применять envelope encryption для минимизации операций с HSM

2. API Gateway:
   - Внедрить кэширование на уровне gateway
   - Использовать connection pooling
   - Настроить circuit breaker для защиты от каскадных отказов

3. Миграция данных:
   - Использовать Change Data Capture (CDC) для инкрементальной миграции
   - Планировать batch-миграцию в off-peak часы
   - Применять blue-green deployment

4. База данных:
   - Правильное индексирование на этапе проектирования схемы
   - Connection pooling (PgBouncer для PostgreSQL)
   - Партиционирование для больших таблиц

5. Мониторинг:
   - Sampling для high-volume логов
   - Агрегация метрик на стороне агентов
   - Retention policies для старых данных

## 6. Заключение

### 6.1 Ключевые выводы

Анализ с использованием диаграммы Исикавы выявил 32 потенциальных узких места в 8 категориях. Наиболее критичными являются:

1. Безопасность данных: отсутствие шифрования и RBAC создаёт compliance-риски
2. Качество данных: ПДн в метаданных требует полной реструктуризации
3. Технологический долг: OLE/Excel требуют полной замены
4. Компетенции персонала: отсутствие опыта современных технологий

### 6.2 Критические факторы успеха

1. Поэтапная миграция: минимизация downtime через инкрементальный подход
2. Data-first: приоритет защиты и миграции данных
3. Compliance-first: соответствие ФЗ-152 на каждом этапе
4. Обучение персонала: инвестиции в развитие компетенций
5. Резервирование: полное резервирование перед любыми изменениями

### 6.3 Следующие шаги

1. Утвердить план мер 1-го приоритета
2. Сформировать команду миграции
3. Провести детальную оценку бюджета
4. Разработать детальный план-график миграции
5. Начать обучение персонала
